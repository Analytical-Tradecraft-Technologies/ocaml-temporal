# Feature coverage and implementation status

This reference describes the source re-audited for #1142 at master
[`7963a9a68e3c`](https://github.com/Analytical-Tradecraft-Technologies/ocaml-temporal/commit/7963a9a68e3c31c876a4c883b290064d40ff9ddc)
on 2026-11-13. That is the same commit as the [live evidence
reference](live-acceptance-coverage.md); it replaces the #491 audit of
`beae10d0a58e` (2026-09-20). It is a master snapshot, not release-candidate
qualification. The SDK is experimental; the current package version is the `0.1.0~rc.1`
release candidate, and no final `0.1.0` has been released. A feature's presence,
focused tests, successful live acceptance, and a release support commitment are
separate evidence levels. [#489](https://github.com/Analytical-Tradecraft-Technologies/ocaml-temporal/issues/489)
tracks the support decision; this audit does not decide that policy.

## Evidence levels

- **Implemented**: the source provides the public API or private mechanism.
- **Focused-tested**: deterministic OCaml/Rust/C tests or source contracts
  exercise the mechanism without a server. Mock client tests do not run workflows;
  `Temporal.Testing` runs them in-process against a server simulator.
- **Live-tested**: a named assertion passed against real Temporal Server and
  PostgreSQL. This applies only to the tested source, pins, topology and scenarios.
- **Supported**: an explicit release policy commits to a scope and compatibility
  matrix. The experimental package has no v1 production support promise yet.

The [live evidence reference](live-acceptance-coverage.md) contains the
commit-pinned test links and the verified [November 10 CI run](https://github.com/Analytical-Tradecraft-Technologies/ocaml-temporal/actions/runs/42926120004).
Its three live shards used Linux OCaml 5.5, Temporal Server 1.32.2 and
PostgreSQL 18.6. The other Linux/compiler and native build lanes are not
additional live-server tests. The [generated inventory](live-acceptance-inventory.md)
lists current fixture membership; historical milestone evidence remains in
[progress](../progress.md).

## Native ownership and recovery

| Mechanism | Evidence boundary |
| --- | --- |
| Private JSON and C/Rust boundary | Bilateral closed-record validation, copied payloads, opaque handles and exact lease correlation have focused tests. Every pinned Core failure-info kind has a variant: application, canceled, terminated, activity, child-workflow, timeout, server, reset-workflow, Nexus-operation and Nexus-handler. A missing failure info is `absent`. A failure kind therefore never rejects an activation, client wait or update outcome. Server, reset and Nexus failures are covered by Core-conversion and shared-fixture tests only; no live controller produces them. The live controllers exercise ordinary and selected failure records; malformed-input/fault-injection coverage remains focused. |
| One-owner supervisor and completion drainage | Mailbox, owner Domain, bounded readiness waits, protocol rejection, retryable completion retention and shutdown tests protect lifecycle rules. A retry does not rerun user code. The baseline also requires client and worker stop markers. |
| Serialized activity execution | One callback is decoded, invoked and completed before another task is admitted. Core is granted one activity slot and one local-activity slot to match, so the server keeps undelivered tasks schedulable instead of starting their timeouts in the bridge queue; at most one remote task can wait behind one local callback. The pools stay separate because Core pre-reserves an idle local-activity permit, which would starve a shared pool. A cancellation task updates the original token and does not create a second completion lease. It cannot preempt a callback already executing under the adapter lock; instead each heartbeat of a running synchronous callback sweeps the ready tasks, delivers that attempt's cancellation to its context, and defers other tasks in order (#494). |
| Worker resource and shutdown options | `Worker.Options.make` validates the sticky cache bound, workflow-task limit, fixed or autoscaling workflow pollers, sticky-queue timeout, shutdown grace period, heartbeat throttle intervals and per-worker/task-queue activity rates (#498). Invalid, overflowing and contradictory values are typed defects returned before any native allocation, and Rust validates the same rules again. `Worker.options` reports the effective values. Focused tests pin the exact bridge document and the Core `WorkerConfig` it produces. The `worker_resource_options` live regression runs a one-workflow-cache, two-slot, one-activity-per-second worker through a saturating burst and a recovery execution. Activity slot counts are not configurable: they stay pinned to the serial executor (#777). Shutdown is bounded by the grace period plus `shutdown_teardown_timeout` (#495): work still running when the grace period ends is abandoned and reported by `Worker.shutdown_with_report`, and the `bounded_shutdown` live regression shows a never-heartbeating activity retried and completed on a second worker. |
| Cooperative activity cancellation and shutdown signal | `Activity.Context.cancellation` exposes a delivered cancellation with Core's typed reasons, heartbeats return a `` `Cancelled `` error after it, and a `` `Cancelled `` result completes the attempt as cancelled only when a cancellation was delivered. A start cancelled before admission completes as cancelled without running; shutdown drain fails an undispatched deferred start retryably. `Context.is_worker_shutting_down` reads the worker's stop flags. Focused adapter tests cover delivery, precedence, before/after cases, drain and deferred poll errors; the `activity_cancellation` live regression covers a workflow-requested cancellation completing as cancelled, a heartbeat-timeout cancellation, and the shutdown signal. `Activity.Async_handle.heartbeat` reports a cancellation request as a non-retryable `` `Cancelled `` error and a pause or reset as a retryable one, while keeping the handle live (#1103); Rust throttle and OCaml adapter tests cover it. The [cooperative cancellation example](../../examples/README.md#cancel-activities-cooperatively), run live by `make test-temporal-examples-live`, cancels a synchronous and an asynchronous activity that each release an idempotent reservation before acknowledging, and shuts a worker down during a synchronous activity so the attempt releases its reservation and a replacement worker commits the retry. Reservation keys include the workflow run ID, and a new run reusing a closed run's workflow ID is shown doing its own work. Asynchronous handles observe worker shutdown through `Async_handle.is_worker_shutting_down` and a retryable `"WorkerShutdown"` heartbeat error, and a completer that fails the handle with it hands the attempt back for retry (#1157; the `bounded_shutdown` live regression verifies this). A handle still unfinished when the grace period ends is closed as lost, an unfinished handle expires per #1043, and Temporal then retries per the attempt's timeouts. A callback that never heartbeats never observes a cancellation. Re-qualification after the isolated activity dispatch of #492 remains. |
| Worker recovery | Separate successful live controllers cover graceful restart, forced crash, one-slot sticky-cache eviction, exact parent/child restart and child failure after replay. Live regressions add a worker killed during a running activity callback (`activity_worker_crash`, #519), query and suspended-update recovery after eviction and worker replacement (`interaction_recovery`, #530) and bounded shutdown with an abandoned callback (`bounded_shutdown`, #495); see the [recovery inventory](live-acceptance-coverage.md#worker-crash-restart-shutdown-and-eviction-inventory). This is a bounded corpus, not arbitrary crash/failure history qualification. |
| Replay feeder and offline replay | Strict history JSON/protobuf validation and bounded Core replay-worker plumbing exist. `Temporal.Replay` exposes them as an offline API with typed nondeterminism, task-failure, invalid/unsupported-history and replay-error results; its public tests replay retained live histories, detect removed or replaced commands, reject malformed input and repeat 140 isolated replays. Nondeterminism results carry a structured mismatch (workflow ID and type, recorded event, matched command, Core's reason), asserted against the corpus negative controls. Live worker replacement separately proves server-delivered replay. The versioned [history corpus](history-corpus.md) replays 38 recorded histories as 88 cases through the public API in every `dune runtest`, including 27 nondeterminism negative controls and 5 malformed-history controls that must be refused as invalid histories; its [feature coverage table](history-corpus.md#feature-coverage) maps each replay-relevant feature to a case or to an explicit not-applicable or not-yet-captured reason (#503). The copyable [replay command example](../../examples/README.md#replay-recorded-histories-before-deploying) wraps the API in an offline CLI with one line per history and distinct exit statuses; `test/replay_cli` checks them against a recorded example history and deliberately changed workflow code. There is no protobuf-JSON history input. |
| Observability | Structured `logs` sources/tags and privacy-safe diagnostics have focused tests. Workflow lease records carry workflow ID, run ID and a replay flag (#500). A shared `Runtime` can export Temporal Core's worker and client metrics on a Prometheus endpoint with the official SDKs' names; validation, exporter lifecycle and a live scrape with label-cardinality checks are tested ([worker metrics](observability.md#worker-metrics)). Activity lease records carry the activity ID, type and attempt ([activity correlation](observability.md#activity-correlation)). The same endpoint exports SDK-side `temporal_ocaml_` series for activity-lane occupancy and duration, admission and refusal, completion retries and bounded-shutdown outcomes, with Rust, OCaml and live tests ([SDK worker metrics](observability.md#sdk-worker-metrics)). The same metrics can instead be pushed to an OTLP collector over gRPC or HTTP/protobuf (#1161), with Rust tests against loopback collector doubles (headers, final export at release, redaction of header values in logs and errors) and a live regression requiring the Prometheus path's families from an in-process collector stub ([OTLP export](observability.md#otlp-export)). Tracing is not exported, by recorded decision until context propagation exists (#1139, #1162; [tracing](observability.md#tracing)), and the production sample deployment with induced failures (#500) remains incomplete; the [benchmark harness](benchmark-harness.md) is exploratory, and no sustained-load evidence exists (#507). |

[native activities](native-activity-execution.md), and the
[live scenario matrix](live-acceptance-coverage.md) for the boundaries of each claim.

## Deferred and unqualified work

- Public TLS trust/mTLS/API-key configuration and secure connectivity acceptance.
  HTTP(S) URL handling alone is not authentication or Temporal Cloud support.
- Protobuf-JSON history input (an SDK-only route is
  `Client.fetch_history`, #1137; CLI JSON exports still need conversion),
  replaying the seeded
  [history corpus](history-corpus.md) across SDK/Core/server upgrades (#524),
  and local-activity, interaction and deployment-routing recovery beyond the
  single live regressions for each (#1156, #530, #1159).
- Concurrency/load/resource qualification and operational guidance. Shutdown
  is bounded (#495), but abandoned callbacks keep running until the process
  exits.
- Cooperative workflow cancellation and durable cleanup (#514). A
  cancellation request closes the run as cancelled in the activation that
  delivers it; workflow code cannot observe it or run cleanup first. The
  proposed [v1 support policy](v1-support-policy.md) excludes it from MVP v1.
- Schedules, Nexus, interceptors, workflow side effects, workflow-level
  priority/fairness and remaining Temporal parity work.
- A release support/compatibility decision, artifact publication/provenance,
  upgrade rehearsal and complete operational qualification. Existing package,
  installed-consumer, license and release-preflight checks are foundations,
  not evidence that a release was delivered.

The [roadmap](../implementation-roadmap.md) retains the long-term target.
Before release, reconcile the factual evidence here with the approved support
policy and retain a successful run at the exact candidate commit.
